# Bound Delivery Hotfix - 2026-10-02

## Report and Cause

The creator reported successful creation without a visible purple Soulbound Sigil.
The normal client and Host & Play server logs both identified Soulmates 0.15.2;
this was not a client/server version mismatch. Those private logs are not included
in the repository.

The server created the Sigil and consumed a Blank Sigil, then sent unsolicited
native SyncEquipment packets to the owner. The installed engine's MessageBuffer
ignores these updates for its local player unless server-side characters or the
native stacking lock apply. The client kept its old inventory despite the success
response. The graphical single-player pass did not exercise this multiplayer path.

## Changes

- Capture inventory immediately before server-side companion transactions and
  send only changed slots to their owner in a dedicated mod response.
- Serialize native items, including ModItem metadata, stack and favorite marker.
- Parse the complete bounded update before modifying the client's inventory;
  reject duplicate slots, truncated items, cursor slot 58 and oversized counts.
- Update the native client inventory cache and acknowledge changed slots through
  SyncEquipment. Preserve unrelated inventory and the client-owned cursor item.
- Use the same delivery helper for creation, cargo deposits and withdrawals,
  wallet transfers, cargo reconciliation and recall.
- Record the creation result code in local Field Notes, without player names.

## Verification

The engine probe captures actual ModPacket bytes from the server handlers and
replays them through client handlers in an isolated installed-engine runtime.
Native SyncEquipment is also replayed through MessageBuffer.GetData to verify
the owner guard. This is a transport fixture, not a live graphical multiplayer
playtest or a network-latency simulation.

The baseline failures cover missing owner delivery, the stale Blank Sigil count,
the client inventory cache, missing changed-slot acknowledgements and the absent
delivered item's save/load identity. The candidate additionally checks single-unit
resource and copper withdrawals, updated same-type Sigil metadata, favorites,
unrelated client pickups, native ItemIO save/load, invalid update atomicity and
wrong-direction message rejection. Existing single-player creation checks remain
in the engine suite.

Expected malformed-input diagnostics appear during negative tests. The isolated
runtime's denied .tmod registry association is unrelated to item delivery.
